## Specification
<!-- SPECIFICATION:BEGIN -->
Breaking change (v3.0.0): replace the three MCP tools `chat`, `consensus`, `conversation` with a single tool named `chat` that takes a `models` array and a `mode` parameter. Remove the `temperature`, `verbosity`, `use_websearch`, `enable_cross_feedback`, `cross_feedback_prompt`, `turn_prompt`, and singular `model` parameters entirely. `check_status` and `cancel_job` remain separate and unchanged in name/schema.

### Tool interface

The unified `chat` tool schema has exactly these properties (required: `['prompt']`):

| Param | Type | Default | Notes |
|---|---|---|---|
| `prompt` | string | — | required |
| `models` | array of string | `["auto"]` | minItems 1 |
| `mode` | enum `chat` \| `consensus` \| `roundtable` | `chat` | validated in-tool (router validation is shallow) |
| `continuation_id` | string | — | unified across modes; mode switching on resume is allowed |
| `files` | array of string | — | unchanged semantics (line ranges etc.) |
| `images` | array of string | — | unchanged |
| `reasoning_effort` | enum none/minimal/low/medium/high/max | `medium` | unchanged |
| `async` | boolean | `false` | stripped from schema when async tools disabled |
| `export` | boolean | `false` | unchanged |

### Mode semantics

- **`chat`** (default): 1..N models invoked in parallel; each responds independently; models never see each other's output. N=1 preserves today's chat behavior including auto-mode provider failover and Codex thread reuse. N>1 returns per-model responses as separate labeled sections; there is no refinement phase.
- **`consensus`**: requires ≥2 *resolved* models. The ≥2 check is applied AFTER auto-expansion, so the default `["auto"]` is valid and expands to the first 3 available providers (today's behavior); an explicit single concrete model is rejected with an error directing the caller to mode `chat`; and if auto-expansion yields fewer than 2 available providers the same validation error is returned. Parallel phase 1, then the cross-feedback refinement phase ALWAYS runs when ≥2 phase-1 responses succeeded (the old `enable_cross_feedback` flag is gone; the old default refinement prompt template becomes the only template).
- **`roundtable`**: today's conversation tool renamed. Models respond sequentially in the given order, each seeing the full transcript (turn-packet packing preserved — SDK providers only see the last user message). One call = one lap; single model allowed (talks to itself across laps). Duplicate model entries allowed only in this mode (rejected in chat/consensus).

### Removed-parameter behavior

- **Web search**: always enabled where the provider+model supports it (`supportsWebSearch` capability gate stays; the `use_websearch` arg gate is deleted in openai/google/xai; the ignore-warnings in claude/codex/copilot and dead destructuring elsewhere are deleted). The model decides per-request whether to actually search — enabling never forces use.
- **Temperature**: removed end-to-end — tool schemas, tool plumbing, `providerOptions`, provider request-builder blocks, `supportsTemperature` capability flags, `interface.js` contract docs, exporter metadata, help text. Providers stop sending temperature; each API uses its own default.
- **Verbosity**: removed from chat schema/plumbing and from `openai.js` (`text: {verbosity}` blocks); OpenAI API default is `medium` anyway, so behavior is unchanged.
- **`cross_feedback_prompt` / `turn_prompt`**: deleted; the hardcoded default templates become the only behavior.

### Acceptance criteria

1. `getTools(config)` returns exactly `{chat, check_status, cancel_job}`; with `disableAsyncTools` it returns `{chat}` with no `async` schema property.
2. `chat.inputSchema.properties` keys are exactly the 9 params above; `required` is `['prompt']`.
3. `rg -w 'use_websearch|verbosity|enable_cross_feedback|cross_feedback_prompt|turn_prompt|supportsTemperature' src/` returns zero matches; `rg -w temperature src/` returns zero functional references.
4. Validation errors: unknown `mode` lists the three valid modes; `mode: consensus` with <2 *resolved* models (a single explicit model, or `["auto"]` when fewer than 2 providers are available) mentions mode `chat` as the alternative; duplicate models rejected in chat/consensus modes (compared case-insensitively via `trim().toLowerCase()`) with a clear message.
5. `mode: chat` with `models: ["a","b"]`: each provider's `invoke` called exactly once (N total); response contains a labeled section per model; no refinement invocations.
6. `mode: consensus` happy path with N models: `invoke` called 2N times (phase 1 + refinement); refinement runs without any flag.
7. `mode: roundtable` passes the adapted conversation-tool test suite (turn order, pre-failed turns for unavailable models, turn-packet message shape, lap continuation).
8. A thread created in one mode can be resumed in another mode without error; stored continuation state always carries `mode`.
9. Unit tests for openai/google/xai assert web-search tooling attaches whenever the model has `supportsWebSearch: true`, with no flag in options.
10. `generateHelpContent` output documents `mode` and contains no Temperature/Verbosity sections.
11. `pnpm run typecheck`, `pnpm run lint`, and `pnpm run test:unit` pass, plus targeted `pnpm test -- tests/tools/chat*.test.js`. (Do NOT rely on `pnpm run validate`: `scripts/validate.js:170,173` runs `npm run test` + `npm run test:providers` — the full real-API suite CLAUDE.md says never to run. CI itself only runs lint + typecheck + test:unit.)
12. Ships as a single PR whose squash commit body contains `Release-As: 3.0.0` and a `BREAKING CHANGE:` footer.

### Out of scope

- No changes to `check_status`/`cancel_job` schemas or names (their display output changes only via `formatStatus.js`).
- No provider model-catalog changes beyond deleting `supportsTemperature` flags (the stale `gpt-5` → `gpt-5.6` default fix comes free via routing consolidation).
- No changes to `continuationStore.js` storage internals (shape of stored state changes; the store itself is generic).
- No new features beyond the merge (no client streaming, no new modes).

## Design
<!-- DESIGN:BEGIN -->
### Architecture

One tool entry with a mode dispatch into two execution engines. The three current tools duplicate the same outer skeleton (validate → async submit or sync run → history load → path validation → context build → invoke → persist → export → token-limit → status line); that skeleton is written once in the unified tool, and only the "resolve models → invoke" core differs per mode:

- **Parallel engine** (serves modes `chat` and `consensus`): generalization of consensus.js's phase runner. Takes a list of *call plans* and runs them concurrently with per-call try/catch and per-call streaming/progress. Mode `consensus` runs it twice (phase 1 + refinement); mode `chat` runs it once.
- **Roundtable engine** (serves mode `roundtable`): conversation.js's sequential turn engine, moved as-is (turn packets, framing, lap transcript rendering), minus the `turn_prompt` injection.
- **Engine/shell contract**: the two engines are execution cores — they resolve/invoke and RETURN invocation data (per-call responses & failures, selected candidate, response metadata/thread IDs, transcript or the combined labeled content, timing/progress). Persistence, export, summaries, token-limiting, and MCP-response construction live once in the unified tool's shared skeleton, NOT inside the engines (TODO 3 moves the roundtable *turn loop*, but its side-effecting tail — persist/export/token-limit — belongs to the shell). **Parallel-engine failover must preserve today's chat auto-behavior:** per call plan, try candidates in order, retry each with the existing `retryWithBackoff`, advance to the next candidate only when `shouldFailoverToNextProvider` permits, and NEVER fail over on an abort; when a streaming candidate fails, clear its `provider_${i}_preview` and any partial accumulated content before starting the next candidate. Multi-model chat needs explicit partial-success / all-failed rules (surface per-model failures like consensus phase 1 does).

**Call plans unify single- and multi-model chat.** Model resolution produces, per requested model, `{modelSpec, candidates: [{provider, model}, ...]}`. In mode `chat`, `"auto"` yields the full provider-priority candidate list and the engine fails over across candidates in order (preserving today's chat auto-failover); an explicit model yields exactly one candidate (no failover, as today). In mode `consensus`, `["auto"]` expands to the first 3 available providers' default models (today's behavior). In mode `roundtable`, `["auto"]` resolves to the first available provider, and unavailable/unknown models stay in the turn plan as pre-failed turns (today's behavior).

### Key decisions

1. **System prompt per mode**: `chat` → `CHAT_PROMPT` at any N (answers are independent; the 1:1 framing holds; the rigid consensus report format would be wrong without a refinement phase), `consensus` → `CONSENSUS_PROMPT`, `roundtable` → `ROUNDTABLE_PROMPT` (renamed from `CONVERSATION_PROMPT`). Selection via a new `getSystemPromptForMode(mode)` export.
2. **Continuation state** unified as `{messages, mode, lastUpdated, ...modeExtras}` where modeExtras are: chat → `{models, providerThreads}` (a `{[threadKey]: threadId}` map generalizing today's `codexThreadId`); consensus → `{consensusData}`; roundtable → `{roundtableData}` (renamed from `conversationData`, same keys). The old `type` field is dropped in favor of `mode`. **`providerThreads` key identity (corrected):** key by a STABLE per-call-plan identifier — the requested model spec exactly as written in `models` (e.g. `"auto"`, `"codex"`) — NOT the resolved provider/model. Keying by resolved model breaks two cases: `["auto","codex"]` (both resolving to codex) would collide on one thread, and a thread stored under the resolved name `"codex"` would not be found next turn when the spec `"auto"` is re-resolved. This key must be threaded explicitly through provider options into `codex.js` (see TODO 7) — the current `getThreadIdFromContinuation(continuationId, continuationStore)` has NO model/spec in scope. `providerThreads` is chat-mode-scoped (mode extras are per-mode, so switching to another mode and back starts fresh threads — acceptable, not promised otherwise). **System-message normalization (new requirement):** each mode owns a different system prompt, and stored histories keep their leading system message (chat, consensus, and roundtable all persist one — e.g. `conversation.js:361-366` reuses a stored leading system message as-is). The shared skeleton must STRIP any stored leading system message and PREPEND exactly one `getSystemPromptForMode(currentMode)` before invoking, then persist that normalized history — otherwise a cross-mode resume runs with the previous mode's prompt (a chat thread resumed as roundtable would keep `CHAT_PROMPT`). Cross-mode resume is allowed by design: the shared `messages` array is the context; the tool applies the current call's mode. In-memory store means no legacy-state migration is needed. **Caveat (documented limitation, not fixed here):** SDK providers codex/claude/copilot consume only the last `user` message, so a thread built in one mode and resumed in `chat`/`consensus` gives those providers only the new prompt — not the prior transcript — as context (API providers receive the full `messages` array). AC8 requires cross-mode resume to succeed *without error*, not full context fidelity for SDK providers; provider-aware final-message packing for chat/consensus is out of scope (flagged in Notes).
3. **Async jobs**: `jobRunner.submit({tool: 'chat', mode, sessionId, options}, ...)`; `asyncJobStore` whitelist narrows to `['chat']` and persists `mode`; `formatStatus.js` branches convert from `jobStatus.tool ===` to `jobStatus.mode ===`. Status lines (SUBMITTED/COMPLETED and cancelJob output) print the MODE uppercase (`CHAT`/`CONSENSUS`/`ROUNDTABLE`) where they printed the tool name, keeping today's output shape.
4. **Progress keys** (flat, since `progress` is reserved as numeric): consensus keeps `consensus_progress` + `provider_${i}_*`; roundtable renames `conversation_progress` → `roundtable_progress` (same companions `total_turns`/`completed_turns`/`current_model`); multi-model chat emits `chat_progress: "x/N"` + the same `provider_${i}_*` keys via the shared parallel engine; single-model chat keeps its flat `provider`/`model` fields.
5. **Result statuses**: `chat_complete` (any N), `consensus_complete`, `roundtable_complete`. Chat N>1 content is labeled markdown sections per model (consensus phase-1 formatting without the refined section). **Persist chat N>1 as a SINGLE combined assistant message** (the per-model labeled sections joined into one message), never one assistant message per model: `anthropic.js:466-473` throws on consecutive same-role messages, so multiple stored assistant messages would break a later resume on Anthropic. This mirrors how consensus already persists one formatted assistant message.
6. **Routing consolidation**: delete the inline `mapModelToProvider`/`resolveAutoModel`/`getDefaultModelForProvider` copies in chat.js/consensus.js; everything imports from `src/utils/modelRouting.js` (fixes the stale `gpt-5` default). The provider-priority list, currently repeated in several places (chat.js, consensus.js's auto-expansion block, modelRouting.js, and referenced from conversation.js), moves into `modelRouting.js` as an exported constant `PROVIDER_PRIORITY`. `summarizationService.js:13` and the two provider tests importing from `tools/chat.js` are repointed.
7. **Context processing**: standardize on the injected `dependencies.contextProcessor.processUnifiedContext` (conversation.js pattern). chat.js imports BOTH `processUnifiedContext` and `createFileContext` directly (chat.js:9-12) but already calls the *injected* `contextProcessor.processUnifiedContext` (chat.js:231,821) while using `createFileContext` directly (chat.js:246,836) — so drop ONLY the unused direct `processUnifiedContext` import and KEEP `createFileContext` (roundtable's source, conversation.js:26-28, also imports it directly). Also drop chat's dead `webSearch` context wiring (the "not yet implemented" placeholder). `processWebSearchContext` in contextProcessor.js is deleted too if nothing else references it (verify at implementation time).

### Context Manifest

#### How This Currently Works: The Three Tools, Registration, and Dispatch

The Converse MCP server exposes five tools. Three of them — `chat`, `consensus`, `conversation` — are the merge targets; `check_status` and `cancel_job` stay as-is. All tools follow the same functional contract: `async function(args, dependencies) => mcpResponse`, with `description` and `inputSchema` attached as static properties on the exported function.

**Registration (`src/tools/index.js`).** The `tools` map (lines 20-26) hard-codes the five tool functions keyed by MCP tool name: `chat: chatTool, consensus: consensusTool, conversation: conversationTool, check_status, cancel_job`. `getTools(config)` (line 33) returns this map, but when `config.async.disableAsyncTools` is set it (a) drops `check_status` and `cancel_job` entirely and (b) for the three model tools clones the tool and deletes the `async` property from a shallow-copied `inputSchema.properties`, wrapping the handler so the stripped schema is advertised. The name check on line 51 (`name === 'chat' || name === 'consensus' || name === 'conversation'`) must collapse to just `'chat'` after the merge. `index.js` also owns the shared response helpers every tool uses: `createToolResponse` (lines 204-283, normalizes a `{content, continuation, metadata}` result object into MCP `{content:[{type:'text',text}], isError}` and hoists `continuation`/`metadata` to the top level), `createToolError` (291), `formatFailureDetails` (188, used by consensus + conversation), and `formatMetadataDisplay` (122, currently unused by the hot path but branches on `metadata.models_list` vs `metadata.provider`).

**Dispatch (`src/router.js`).** `createRouter` registers a single `CallToolRequestSchema` handler (line 201). It looks up the tool via `validateTool` (line 71 — throws `RouterError` with "Unknown tool" listing available tools), then runs `validateToolArguments(toolArgs, tool.inputSchema)` (line 493). **Critical constraint: this validator is shallow.** It checks `required` presence, JSON-Schema `type` per property, and string `minLength`/`maxLength` only — it does NOT validate `enum` values, array `minItems`, or `default`. So a new `mode` enum (`"chat"|"consensus"|"roundtable"`) will NOT be enforced by the router; the merged tool must validate `mode` itself and reject/normalize unknown values, exactly as the tools today manually validate `prompt` and `models`. The tool is then invoked as `tool(toolArgs, { ...dependencies, signal: extra?.signal })` where `signal` is the per-request `AbortSignal` from the MCP SDK. `dependencies` is built once in `createDependencies` (line 108): `{config, continuationStore, providers, contextProcessor:{processUnifiedContext}, asyncJobStore, jobRunner, fileCache, providerStreamNormalizer, sessionId:'local-user', router}`. `ListToolsRequestSchema` (line 277) enumerates `tools` into `{name, description, inputSchema}` — so whatever the merged `chat` schema says is what MCP clients see.

**Note the `dependencies` shape mismatch:** the sync tool paths destructure `contextProcessor` and call `contextProcessor.processUnifiedContext(...)`, but chat.js *also* imports `processUnifiedContext`/`createFileContext` directly from `../utils/contextProcessor.js` (chat.js lines 9-12) yet uses the injected `contextProcessor` in practice. consensus.js and conversation.js use the injected one. The merged tool should standardize on `dependencies.contextProcessor.processUnifiedContext`.

#### The Three Execution Flows — What They Share vs Duplicate

All three tools have the identical outer skeleton, which is where most of the duplication (and the merge opportunity) lives:
1. Destructure deps + validate `prompt` (consensus/conversation also validate `models` is a non-empty array).
2. **Async branch** (`if (async)`): validate `jobRunner`/`providerStreamNormalizer` present; validate custom `continuation_id` via `isSafeIdSegment`; generate/reuse `continuation_id`; compute `isCustomId` (non-standard format AND not already in store); generate a title via `SummarizationService.generateTitle(prompt)`; call `jobRunner.submit({tool, sessionId, options:{...args, jobId, ...}}, async (context) => execute…WithStreaming(...))`; return an immediate `⏳ SUBMITTED | <TOOL> | <id> | 1/1 | Started: … | "<title>" | <models>` status line plus `continuation_id`.
3. **Sync path**: load history from `continuationStore.get(continuation_id)`; `validateAllPaths({files,images})`; build a context message from files/images (and, for chat, web search placeholder); assemble provider `messages`; resolve model(s)→provider(s); invoke; persist state; optionally `exportConversation`; token-limit; return a `✅ COMPLETED | <TOOL> | …` status line + `continuation_id` + content.

**chat (`src/tools/chat.js`, `chatTool` line 40).** Single model. Params destructured lines 58-70: `prompt, model='auto', files, continuation_id, temperature=0.5, use_websearch=false, images, reasoning_effort='medium', verbosity='medium', async, export`. Uses `CHAT_PROMPT` as the system message (only added if history has no leading system message — lines 267-275). Auto mode builds `providerCandidates` in priority order `[codex, gemini-cli, claude, copilot, openai, google, xai, anthropic, mistral, deepseek, openrouter]` (line 306), skipping text-only providers when images are present (`providerSupportsImages`), and does retry-with-failover across candidates via `retryWithBackoff` + `shouldFailoverToNextProvider` (lines 364-403). Non-auto resolves one provider via the LOCAL `mapModelToProvider` (line 572 — a full copy of the routing logic, **also exported and imported by `src/services/summarizationService.js` line 13**). `providerOptions` passed to `invoke` (line 370): `{model, temperature, reasoning_effort, verbosity, use_websearch, signal, config, continuation_id, continuationStore}`. Persists `{messages, provider, model, lastUpdated, codexThreadId}`. Async streaming variant is `executeChatWithStreaming` (line 741): near-duplicate of the sync body but drives the provider stream through `providerStreamNormalizer.normalize(...)`, accumulating `delta`/`reasoning_summary`/`usage`/`end` events and calling `context.updateJob({accumulated_content, progress:{phase, provider, model}, reasoning_summary})`; generates a final summary via `generateFinalSummary` when content > 100 chars.

**consensus (`src/tools/consensus.js`, `consensusTool` line 43).** N models in parallel + optional cross-feedback. Params lines 71-84: adds `models` (required array), `enable_cross_feedback=true`, `cross_feedback_prompt`, `temperature=0.2` (note different default from chat), drops the singular `model`, `verbosity`. Uses `CONSENSUS_PROMPT` (always added as system message, line 273). Single `["auto"]` expands to the first 3 available providers' default models (lines 302-356). Builds `providerCalls[]`, then Phase 1 = `Promise.allSettled` over `provider.invoke(messages, options)` (line 417). Phase 2 (if `enable_cross_feedback && successful>1 && !aborted`, line 474) builds a per-model feedback prompt embedding every other model's answer and re-invokes each model with `[...messages, {assistant: initialResponse}, {user: feedbackPrompt}]`. Persists a *formatted-markdown* assistant message (`## Initial Responses` / `## Refined Responses` / `**Summary:**`) with `type:'consensus'` and a `consensusData` block. Result object (line 684) is structured: `{status:'consensus_complete', models_consulted, successful_initial_responses, failed_responses, refined_responses, phases:{initial, refined?, failed}, continuation, settings}`. Local copies of `mapModelToProvider` (line 780), `resolveAutoModel` (772), `getDefaultModelForProvider` (751). Async variant `executeConsensusWithStreaming` (line 949) + shared-phase helper `executeConsensusPhaseWithStreaming` (line 1512) which streams every provider concurrently, maintaining `provider_${i}_status/_preview` and a combined `accumulated_content` joined by `\n\n---\n\n`, and emitting `consensus_progress` = `"x/N initial"|"x/N refined"`.

**conversation (`src/tools/conversation.js`, `conversationTool` line 386).** N models sequentially (round-table). This is the newest tool and is the cleanest reference: it already imports the shared routing helpers from `../utils/modelRouting.js` (lines 41-47) instead of copying them. Params lines 418-430: `models` (ordered, required), `temperature=0.2`, `reasoning_effort`, `use_websearch`, `turn_prompt` — no `enable_cross_feedback`/`cross_feedback_prompt`, no singular `model`, no `verbosity`. Uses `CONVERSATION_PROMPT`. Key mechanic and **critical provider constraint (documented at conversation.js lines 14-19):** SDK providers (codex, claude, copilot — NOT gemini-cli, which serializes the full array) reduce the message array to ONLY the last `user` message, so each turn packs the entire context (prior-lap transcript + lap prompt + same-lap turns + framing) into ONE self-contained final user message ("turn packet", built by `buildTurnPacket` line 144; framing by `buildFramingText` line 108). Prior laps are re-rendered from stored state into labeled text by `renderStoredTranscriptToText` (line 60). `resolveTurnPlan` (line 207) keeps unavailable/unknown models in-order as pre-failed turns (unlike consensus which drops them). One tool call = one lap; `continuation_id` drives more laps. Persisted state (`buildConversationState` line 352) uses `type:'conversation'`, pairs a user (lap prompt) message with an assistant (full lap transcript) message, and preserves a leading system message. Result (line 732): `{status:'conversation_complete', content:<transcript>, models_consulted, successful_turns, failed_turns, turns[], continuation, settings}`. Async variant `executeConversationWithStreaming` (line 895) + `executeTurnWithStreaming` (line 784); uses FLAT progress keys (`conversation_progress`, `total_turns`, `completed_turns`, `current_model`) plus a numeric `progress` fraction — the comment at lines 1037-1040 warns that `asyncJobStore.update()` treats the reserved `progress` key as a numeric 0..1 value, so per-turn detail must NOT go under a `progress` object (this is why consensus uses `provider_${i}_*` flat keys too).

**Duplication summary for the merge:** the outer async/sync skeleton, file/image context building, history load, path validation, title/summary generation, token limiting, export, and status-line formatting are near-identical across all three. Routing helpers exist canonically in `src/utils/modelRouting.js` but chat.js and consensus.js each carry stale inline copies (e.g., consensus's local `getDefaultModelForProvider` still defaults to `gpt-5`, whereas `modelRouting.js` line 16 was updated to `gpt-5.6`). #### continuationStore: Thread Format and Cross-Tool Compatibility

`src/continuationStore.js` is an in-memory `Map`-backed singleton (`getContinuationStore()` line 274; max 1000 conversations, max 100 messages each, hourly cleanup, 24h TTL). `set(id, state)` shallow-merges `lastAccessed`/`createdAt` metadata and truncates `state.messages` to the last 100. `get(id)` strips internal metadata and returns `{...cleanState, _metadata}` or `null`. `generateContinuationId()` → `conv_<nanoid(10)>`. `isValidContinuationId` accepts `conv_<10 url-safe>` or legacy `conv_<uuid>`. The stored **state shape is NOT uniform across tools**: chat stores `{messages, provider, model, lastUpdated, codexThreadId}`; consensus stores `{messages(with a single formatted-markdown assistant message), type:'consensus', consensusData}`; conversation stores `{messages(user=lapPrompt / assistant=lapTranscript pairs, leading system msg), type:'conversation', conversationData}`. The `messages` array is the only field every reader relies on. This matters for the merge because a `continuation_id` created in one mode may be resumed in another mode: today the tools don't enforce mode-consistency, and `renderStoredTranscriptToText` (conversation) is the only reader that deeply parses the stored user/assistant pairing. The planner must decide whether the unified tool records the `mode` in state and whether/how cross-mode resumption is allowed (e.g., a chat thread resumed as roundtable). `addMessageToHistory` (line 363) is exported but only chat/consensus import it (and don't actually call it in the hot path).

#### use_websearch / temperature / verbosity Plumbing and Capability Flags

These three params flow from tool args into `providerOptions` and are consumed inside each provider's `invoke`/stream methods, gated by per-model capability flags in each provider's model-config table.

- **`use_websearch`** (to become always-on where supported): each provider's model config carries `supportsWebSearch: true|false`. Only OpenAI, Google, and XAI actually attach web-search tools. In `src/providers/openai.js` (line 526): `if (use_websearch && modelConfig.supportsWebSearch) requestPayload.tools = [{type:'web_search_preview'}]`; response metadata records `web_search_used`/`web_search_type` (lines 757, 776). `src/providers/google.js` (line 583) attaches grounding when `use_websearch && supportsWebSearch`; XAI similarly. Codex, claude, gemini-cli, anthropic, mistral, deepseek all set `supportsWebSearch:false` (they either access files directly or don't support it). **The spec change ("always-enabled where the provider supports it; the model decides whether to search") means the plumbing keeps the `supportsWebSearch` gate but drops the `use_websearch` arg gate** — i.e., pass `use_websearch: true` (or a constant) into providers unconditionally, or refactor providers to attach the tool whenever `supportsWebSearch`. Note `gpt-5-nano` has `supportsWebSearch:false` and is the default `SUMMARIZATION_MODEL`, so summarization calls won't attach search.
- **`temperature`** (to be removed): gated by `supportsTemperature`. Most modern models set `supportsTemperature:false` (GPT-5 family, Fable 5, Codex/Claude/Gemini SDKs manage it internally). Providers apply it as `if (temperature !== undefined && modelConfig.supportsTemperature !== false) payload.temperature = temperature` (e.g., anthropic.js line 711, openai.js line 533, google.js line 502, openai-compatible.js line 373). Removing the arg means these blocks receive `undefined` and skip — safe, but the arg should stop being forwarded and the schema entries removed. `exportConversation` and its metadata writer also consume `temperature` (see below).
- **`verbosity`** (to be removed): chat-only today. Only OpenAI applies it — `if (resolvedModel.startsWith('gpt-5') && verbosity) requestPayload.text = {verbosity}` (openai.js lines 551, 588). Removing it means GPT-5 calls fall back to the API default.

Capability flags live per-model in: `src/providers/openai.js`, `google.js`, `xai.js`, `anthropic.js`, `codex.js`, `claude.js`, `gemini-cli.js`, `mistral.js`, `deepseek.js`, `openrouter.js`, and the shared base `openai-compatible.js`. `src/prompts/helpPrompt.js` reads these flags (lines 225, 394-395) to auto-generate the "Web Search" / "Temperature" feature lists and reads `tools.chat.inputSchema.properties.temperature` (line 272-276) to document params — so removing `temperature`/`verbosity` from the schema will change help output and helpPrompt.js may need updating.

#### Async Job Creation and Per-Mode Progress Formats

`jobRunner.submit(jobSpec, runFunction, options)` (`src/async/jobRunner.js` line 92) stores `jobSpec.tool` and `jobSpec.sessionId` into job state and runs `runFunction(context)`; `context` exposes `updateJob(patch)`, `signal`, `jobId`. **The `tool` field is the load-bearing coupling for status display.** `src/utils/formatStatus.js` branches on `jobStatus.tool` to render progress: `formatHumanReadableStatus` (line 111) does `if (tool === 'consensus') …consensus_progress/models_list`, `else if (tool === 'conversation') …conversation_progress turns/models_list`, `else if (tool === 'chat') …provider/model`. `formatJobListHumanReadable` (line 19) similarly special-cases `tool === 'consensus'` for `consensus_progress` and provider='multiple'. `formatJobStatus` (line 328) surfaces `consensus_progress`, `conversation_progress`, `models_list`, `provider`, `model`, plus consensus `provider_${i}_preview` collection (lines 358-368). **After the merge every job's `tool` will be `'chat'`, collapsing all three display branches into one.** The planner must decide how mode reaches formatStatus: either store `mode` on the job (e.g., pass it in `jobSpec` / `updateJob`) and rebranch formatStatus on `mode`, or keep emitting the existing progress keys (`consensus_progress`, `conversation_progress`) and branch on their presence. The initial `⏳ SUBMITTED | <TOOL> | …` lines the tools print themselves (chat.js line 167, consensus.js line 176, conversation.js line 516) will all say `CHAT` unless they incorporate the mode. `check_status`/`cancel_job` consume this: `cancelJob.js` (line 129) prints `jobState.tool.toUpperCase()`; `checkStatus.js` routes through the formatStatus helpers. These two tools don't otherwise need changes since they key off `continuation_id`, but their output strings will reflect the collapsed tool name.

`exportConversation` (`src/utils/conversationExporter.js`, exported line 194) accepts an options bag currently including `temperature, verbosity, use_websearch, enable_cross_feedback` (destructured lines 199-206, written into metadata lines 162-182, 257-264). **Planner decisions:**
- Temperature removal is full-depth (provider request builders + `supportsTemperature` flags), not just tool-level: a param no caller can set is dead plumbing. APIs fall back to their own defaults; the flagship CLI/SDK providers ignored temperature anyway, so the effective change is confined to older API models (0.5/0.2 → API default).
- Verbosity removal is behavior-neutral: openai.js only sent it for GPT-5 models with default `medium`, which is the API default.
- Mode `chat` uses `CHAT_PROMPT` at any N; `CONSENSUS_PROMPT`'s rigid report format only makes sense with a refinement phase.
- Cross-mode continuation is allowed (the transcript is shared context) — this deliberately enables the chat → consensus/roundtable escalation pattern. Stored state gains `mode`; the in-memory store means no migration. (Caveat: SDK providers see only the last user message on resume — see Design decision 2 and the scope note below.)
- `codexThreadId` generalizes to `providerThreads: {[threadKey]: threadId}`, keyed by the requested model-spec (Design decision 2), so N-model chat keeps Codex thread reuse per call plan.
- Single task, not split: every push to main auto-releases (always-bump-patch), so the breaking change must land in ONE push with `Release-As: 3.0.0` — splitting would publish intermediate breaking patch releases. The change is one cohesive interface redesign; provider edits are mechanical.
